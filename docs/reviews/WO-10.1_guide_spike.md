## Answer

Use **GuideNH's export as the 3D view, framed, never embedded or vendored**. Clayton runs
`/guidenhc exportsite` in a Lab client and copies the folder to `GOS_HOME/data/guide-site/`; the core
serves it unchanged under `/guide/` and the Build view shows a scene page in an `<iframe>` whose own CSP
limits which files it loads to `/guide/`. **Framing is not isolation yet**: the frame is same-origin
with the dashboard, so the folder's scripts are trusted (see "Trust boundary" below); WO-10.8 moves
`/guide/` to its own origin. GOS's own panels (WO-10.8: checklist, materials, BOM,
hatch slots) sit beside the frame and key blocks by `registry@meta` from our DB, not from GuideNH's
hover payload. MrBruh's approach (our own three.js viewer, re-implemented, Apache-2.0 attribution) stays
the fallback if the real export fails in the Lab (V15 still needs Clayton's run).

## What `exportsite` writes (source at 1.3.55)

- Command: `/guidenhc exportsite [outDir] [--ponder-frames | --ponder-every-tick]`
  (`client/command/GuideNhClientCommand.java`). A **client chat command only**: no system property or
  startup hook runs it (the only startup properties are `guideme.showOnStartup` and
  `guideme.validateAtStartup`). Default `outDir` is `config/guidenh/site-export/<yyyyMMdd-HHmmss>/` in the
  game folder (`GuideSiteOutputPaths`).
- It exports **every registered guide** (`GuideRegistry.getAll()` in `GuideSiteExportTask`), not one page.
  A guide of our own goes in `config/guidenh/DefaultGuide/<modid>/guidenh/_en_us/*.md` (wiki
  Getting-Started; the folder is made on the client automatically).
- Layout (`GuideSiteWriter`, `GuideSiteAssetRegistry`):
  - `index.html`, `site-config.json`, `SITE-CONFIG.md`; one `.html` per guide page and language.
  - `_site/`: the viewer and site code copied from the jar, about 1 MB (`model-viewer/vendor/modelViewer-*.js`
    529 KB with three.js inside, `app.js` 66 KB, `app.css` 62 KB, `modelViewer.js` 60 KB, fonts ~140 KB).
  - `_res/<bucket>/<sha256>.<ext>`: content-addressed shared files: `scenes/*.scene.gz` (GuideME FlatBuffers
    `ExpScene`, gzip), `placeholders/*.png`, `templates/*.html.gz` (tooltips), hover JSON, item icons.
  - An optional `npm run build` in the export (sharp, parse5, postcss) re-encodes images; not needed to view.
- A page shows a scene as `<img class="game-scene" data-scene-src="{{root}}/_res/scenes/…scene.gz" data-scene-*>`
  (`GuideSiteSceneTagRenderer`), hydrated by `setupGameScene(node)` from `_site/model-viewer/modelViewer.js`.
- **Multiblock at a tier**: `<GameScene><ImportStructureLib controller="gregtech:gt.blockmachines:<id>" tier="4"/></GameScene>`
  (registry name + item meta, never a numeric block id). The exporter **precomputes one scene file per state**:
  every visible layer x every tier (capped at 8, `MAX_SCENE_STRUCTURE_TIER`) x every channel value (capped at 8),
  keyed `layer=…|ponder=…|structure:…|tier=…|channel:…=…`, plus a state manifest the viewer switches between.
  So size grows with layers x tiers x channels; a fixed `tier` with `locked={true}` keeps one tier.
- **Size: not measured** (needs the real run). The fixed part is ~1 MB; scenes and the shared texture atlas
  readback (`GL11.glGetTexImage`) are the unknowns, and every pack guide is exported too.
- Captures need a GL window: Tessellator mixins record what the client draws (research G §1.1, §1.2).

## Can the dashboard show it? (core Host/Origin rules and CSP)

The viewer was read for what it needs from the page:

| need | GuideNH viewer | dashboard page CSP (`api/dashboard.py`) | `/guide/` frame CSP (this spike) |
|---|---|---|---|
| module scripts, dynamic `import()` | yes, same origin | allowed | allowed, `/guide/` only |
| `eval`, `new Function`, workers, `blob:` URLs, wasm | none found | n/a | not allowed |
| fetch scenes, hover JSON, templates | same origin, gunzips itself (`DecompressionStream`, MIT/Zlib fallback) | `connect-src 'self'` | the frame's own `fetch`: `/guide/` only (its `fetch('/api/…')` is refused); `window.parent.fetch` is **not** limited (trust boundary below) |
| `<base href>` in every page | yes | `base-uri 'none'`: **blocked** | `base-uri 'self'` |
| inline `style=` / `innerHTML` with styles | yes (annotation bubbles, layout boxes) | `style-src 'self'`: **blocked** | `'unsafe-inline'` for styles only |
| tooltips from `<template id>` in the page (`app.js`) | yes | would have to be copied in | the page has them |

So **embedding** the viewer into the dashboard page would mean loosening the dashboard's CSP and copying
GuideNH's tooltip templates and styles in (and loading LGPL code into our bundle's page); **framing** a
whole exported page needs none of that. The frame's headers (`gregtec.build.guide.frame_headers`):
`default-src 'none'`; `script-src`, `connect-src`, `font-src`, `media-src` = `<origin>/guide/`; `img-src`
`<origin>/guide/ data:`; `style-src <origin>/guide/ 'unsafe-inline'`; `base-uri 'self'`;
`frame-ancestors 'self'`; `X-Frame-Options: SAMEORIGIN`. The origin is built from a Host the security
layer has already accepted. `.gz` files go out as `application/octet-stream` **without**
`Content-Encoding` (the viewer gunzips them; a browser that did too would break it). `/guide/` needs a
credential like `/api` (the paired browser's cookie goes with the frame's requests), and the path guard is
the dashboard's own `_file` (no `..`, no links out, no `:`). The iframe's `sandbox="allow-scripts
allow-same-origin"` blocks popups, forms and top navigation.

### Trust boundary (corrected after review)

Neither the sandbox nor the frame CSP isolates the guide from the dashboard. The frame is same-origin,
and CSP is checked against the global whose `fetch` is called, so a script in the frame that calls
`window.parent.fetch('/api/state')` runs under the dashboard's `connect-src 'self'` and gets the state
with the paired device's cookie (and could POST). It can also read the parent's DOM, and GuideNH's
`app.js` writes its keys into the dashboard origin's `localStorage` (harmless today, but coupling). The
same holds for a `/guide/…html` opened as a top-level page. The e2e test pins this down
(`parent.fetch` returns 200) so it stays visible.

What the frame CSP does do: it limits which files the page loads (scripts, styles, images, fonts and its
own `fetch` to `/guide/`), and with no `'unsafe-inline'` in `script-src` it blocks inline-script XSS
through GuideNH's tooltip `innerHTML`. So the remaining risk is the `.js` files in the folder, and the
boundary today is **the folder's contents**: only Clayton's own, unmodified export from his Lab client goes
into `GOS_HOME/data/guide-site/`.

The fix belongs to WO-10.8 and D304 requires it: serve `/guide/` from **its own origin** (a second
allowed host name or port that the `gos_device` cookie is never sent to), with its own credential (a
short-lived signed path token, or loopback/tailnet only), never the dashboard cookie. Dropping
`allow-same-origin` or adding `sandbox` to the CSP is not the fix: GuideNH's `app.js` calls
`window.localStorage.getItem` unguarded, which throws in an opaque origin, and its module scripts and
fetches would then need CORS and lose the cookie.

Two more things a real export has that the stand-in does not:

- `_res` files are named with their source resource's extension, or `.bin` without one
  (`GuideSitePageAssetExporter.extensionOf`), so the fixed type table also serves `.bin`, `.jpg`/`.jpeg`,
  `.gif`, `.ttf`/`.otf`, `.mcmeta` and `.txt`. Anything else is a 404: Lab step 5 checks for them.
- The export holds every guide in the pack. The Build view opens a page under `gos/` (Lab step 2's
  page) first, and `/api/guide` parses every page on each call; WO-10.8 caches that scan (for example
  on the folder's mtime).

Hover: GuideNH's hover targets carry a block position and a tooltip template id (`GuideSiteSceneHoverTargetSerializer`),
not `registry@meta`. The item tooltip names the block; GOS's own "registry ID on hover" and the checklist must
come from our footprint (WO-10.2) by position.

## Licences

- GuideNH: **LGPL-3.0** (`LICENSE.txt`). Its viewer bundle contains three.js (MIT, header kept) and GuideME
  viewer code; `decompressFallback` is MIT AND Zlib. Serving Clayton's own, unmodified export from his disk at
  runtime is use, not vendoring: nothing of it is committed, copied into `core/` or `dashboard/`, or shipped by
  `gos deploy`. Copying or modifying the viewer into the dashboard **is** vendoring and stays out (CLAUDE.md).
  Reading `ExpScene` ourselves later would be re-implementing from the format.
- MrBruh: **Apache-2.0**. Its previewer writes one HTML file that loads three.js 0.160.0 from unpkg through an
  inline import map and inline script, which our CSP forbids; re-implementing it means three.js (MIT) from npm
  in the dashboard bundle, his texture baking ported with attribution, and textures from the pack at runtime
  (never committed). Several days of WO-10.8 work instead of none for the 3D part.

## Lab steps (Clayton's PC)

1. Start the Lab client (`uv run gos launch lab`), open a creative Lab world.
2. In the Lab instance's game folder, create
   `config/guidenh/DefaultGuide/gos/guidenh/_en_us/index.md` with:

   ````md
   ---
   navigation:
     title: GOS build guide spike
   ---

   # EBF (spike)

   <GameScene zoom="2" interactive={true}>
     <ImportStructureLib controller="gregtech:gt.blockmachines:<meta>" tier="1" />
   </GameScene>
   ````

   Replace `<meta>` with the Electric Blast Furnace controller's item meta, read in the Lab client: turn
   advanced tooltips on (F3+H) and hover the controller in NEI; use the number **after** the slash in
   `(#id/meta)`, never the numeric id before it (it is EndlessIDs-assigned). The report
   gives no number on purpose: game numbers come from the DB or the game, never from a doc. Open the guide
   in game once to see the page renders.
3. In chat: `/guidenhc exportsite`. Note the folder it prints (`config/guidenh/site-export/<timestamp>/`),
   how long it took and the folder's size (Explorer, Properties), and how many `_res/scenes` files it has.
4. Copy that folder's contents to `GOS_HOME\data\guide-site\` (so `index.html` is directly inside it).
   Copy only that export, unmodified: the folder's scripts run with the dashboard's access (trust boundary
   above).
5. Open the dashboard, Build (`#/build`): it should open "GOS build guide spike" (the `gos/` page); if not,
   pick it in the page list. Rotate, hover, use the layer slider and the tier/hatch controls in the frame.
   Open DevTools (F12): on Network, filter `/guide/` and note any 404 (name and extension); on Console, note
   CSP reports. Then put the answers under V15 / D304 in the PR: does it render and hover, size, time, the
   404s and CSP reports, and how many pages the list shows.
