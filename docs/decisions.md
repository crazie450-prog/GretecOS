| D115 | 2026-11-06 | WO-2.1 core service | How the core service is built. (1) **Two processes.** `gos-supervisor` (stdlib only) starts, watches and restarts the core; the core is FastAPI + uvicorn on `127.0.0.1:[core] port` (8765). `[core] host` accepts only `127.0.0.1` (plan 4.6; the 4.2 LAN move stays a later, documented exception). The supervisor has its own JSON control port, `127.0.0.1:[core] supervisor_port` (new key, default 8766), so `/health`, `gos stop` and `gos launch` work while the core is down; it refuses any request with a non-loopback `Host` or with an `Origin` or `Sec-Fetch-*` header (a browser). (2) **Restarts.** A managed process that exits, or whose `/health` fails for 20 s, is restarted after 1, 2, 4, 8, 16, 30, then 60 s; a run of 60 s resets the back-off, so a crash after a good run restarts after 1 s (measured in this container: 1.8 s from the kill to a core answering `/health`, in each of 5 runs: the 1 s back-off, start-up and the first probe). A start with no good `/health` in 30 s counts as failed. Every exit, restart and back-off is in the supervisor's status table, which the core serves as the health strip data (`GET /api/health`, pushed on `/ws`). (3) **Stopping.** The supervisor stops a process with a `stop` line on its stdin, then kills it after 5 s; the core also stops when its stdin closes, so it never outlives the supervisor. Children run with GOS_HOME as their working folder, never inside `GOS_APP\current`. `gos stop` stops the managed processes and keeps the supervisor (plan 7.16); `gos serve` starts them again, or runs a supervisor in the foreground (`--detach` in the background, `--core-only` for the core alone); `gos stop --all` also stops the supervisor. (4) **Run files and tokens.** Each process writes `GOS_HOME\run\<supervisor\|core>.json` (pid, port, a fresh admin token per start); `run\` inherits GOS_HOME's ACL, which gives gos-dev nothing.
